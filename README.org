*Organize your e-mails without sacrificing your privacy*

Plauna is a privacy-focused service that helps you categorize your e-mails. Its data remains in storage that you control.

You can parse your e-mails from mbox files or directly by connecting to your IMAP servers. Plauna helps you categorize your e-mails and automates the process so that incoming e-mails are moved to their respective folders on your IMAP server.

*IMPORTANT:* Plauna is still under heavy development at the moment. The features are subject to change.

* Features

- You own 100% of your data. Everything is on your machine.

- You define your categories: Use as many or few as you like

- Multi-language support.

- Support for multiple IMAP connections.

- A responsive statistics dashboard for e-mail volume, MIME types, detected languages and category coverage.

- Upload data from mbox archives.

- Read e-mails directly from IMAP folders.

- Login-name-and-password-protected web UI (the login name defaults to =root=; the password can be set via an environment variable, changed in the UI, or auto-generated on first launch).

- Per-category destination folders: choose exactly which IMAP folder each category's mail is moved to.

- Responsive web UI that also works on mobile, so you can recategorize e-mails on the go.

- Re-fetch an individual e-mail from the IMAP server to fill in content that was missed when it was first read.

- Automatic catch-up on reconnect: because live monitoring relies on IMAP IDLE (which only pushes mail that arrives while connected), every time a connection is (re)established - at startup, after a manual reconnect, or after the health check restores a dropped connection - Plauna re-reads the most recent messages in the monitored folder to save and categorize anything that arrived while it was offline. Already-stored e-mails are skipped, so nothing is duplicated. For a gap larger than that window, use the manual folder Parse.

- SQLite and MariaDB support. MariaDB installations use an automatically managed FULLTEXT index for fast body searches, with correct fallbacks for short words and stopwords.

- Excel-style, faceted filters for subject, sender, recipient and category, plus body search and an inclusive date range. Active filters remain visible and can be removed individually.

- Choice of Naive Bayes or Maximum Entropy (MaxEnt) categorization. Newly trained models combine sender address, sender domain, subject and a bounded part of the message body.

- Safe model switching: existing category assignments can seed the first training of a new model, while the previous model remains active until training succeeds.

- Automatic daily training at a configurable local time, including catch-up after a missed scheduled run.

- Language and category confidence values displayed as percentages with two decimal places.


* What Plauna is NOT

Plauna is not an e-mail archive tool. It saves headers, extracted text and attachment metadata that may be useful for categorization, but it does not preserve binary attachment content or guarantee a complete copy of the original message. Do not rely on Plauna to preserve e-mails that you need to archive.

* How to get Plauna

** Docker

This fork does not publish a pre-built Docker image. Build the container locally from the checked-out repository:

#+begin_src
docker build -t plauna:local .
#+end_src

To explicitly build an x86-64 image on another architecture, add =--platform linux/amd64=:

#+begin_src
docker build --platform linux/amd64 -t plauna:local .
#+end_src

The multi-stage Dockerfile builds the web assets, runs the complete test suite and creates the standalone application jar before producing the runtime image.

Persist =/var/lib/plauna= as a Docker volume. It contains the SQLite database when SQLite is used, =settings.json=, =db-config.edn= and the training/model files. MariaDB stores the e-mail database itself outside this volume, but the settings and model files still need it.

** Build from source

The second way to get Plauna is fetching it from the git repository and compiling using Clojure CLI with the command:

#+begin_src 
clojure -T:build uber
#+end_src

This produces =target/plauna-standalone.jar=. Run it with Java 21 or later (required for virtual thread support). The Dockerfile currently builds and runs it with Java 25.

* Security

The web UI is protected by one configurable login name and password (see "Web UI Password Protection" below). There are no separate user accounts - Plauna is made to be used by self-hosters who own and use the service themselves.

The password protects the UI, but Plauna still has no transport encryption of its own and is meant to run inside a trusted, isolated network.

The Docker image runs Plauna as the unprivileged =plauna= user.

*Please do not expose Plauna directly to the internet. If you must reach it from outside, put it behind a reverse proxy with HTTPS.*

* How to use

** Configuration

The following runtime values cannot be changed from within Plauna:

- The data folder, where the SQLite database (when used), settings and training/model files live. It defaults to =/var/lib/plauna=.
- The server port. It defaults to =8080=.
- An optional application configuration file.

The Docker image creates =/var/lib/plauna= automatically. When running the jar directly, create the configured directory before starting Plauna.

*** Environment Variables

The runtime configuration accepts =DATA_FOLDER=, =SERVER_PORT= and =CONFIG_FILE=.

You can also set the web UI password with =PLAUNA_PASSWORD= and allow selected mTLS client
certificates through a trusted reverse proxy (see "Web UI Password Protection" below).

Database connection can be configured via environment variables (see "MariaDB" below).

*** CLI Parameters

The corresponding CLI parameters are =--data-folder=, =--server-port= and =--config-file=.

For example:

#+begin_src
java -jar plauna-standalone.jar --data-folder /srv/plauna --server-port 8080
#+end_src

*** Application configuration file

The optional application configuration file uses EDN. It can provide the same runtime values and can also contain legacy IMAP client definitions that Plauna imports when the connections table is empty. For new installations, configure IMAP accounts in the web UI instead of storing their secrets in this file.

#+begin_src clojure
{:data-folder "/srv/plauna"
 :server {:port 8080}}
#+end_src

Select this file with =--config-file /path/to/config.edn= or =CONFIG_FILE=/path/to/config.edn=.

*** settings.json

Application preferences are stored in =settings.json= in the data directory (default =/var/lib/plauna/settings.json=). The file is created automatically on first startup. Edit the user-facing values through "Admin" → "Preferences" so they are validated and scheduler changes take effect immediately.

Example file with the user-facing keys (the initial =time-zone= is the host system's zone):

#+begin_src json
{
  "log-level": "info",
  "language-detection-threshold": 0.8,
  "categorization-threshold": 0.65,
  "categorization-algorithm": "naive-bayes",
  "client-health-check-interval": 60,
  "automatic-training-time": "02:00",
  "time-zone": "Europe/Berlin"
}
#+end_src

- =log-level= — =error=, =info=, or =debug=.
- =language-detection-threshold= — confidence (0–1) below which a language is not assigned; default 0.8.
- =categorization-threshold= — confidence (0–1) below which a category is not assigned; default 0.65.
- =categorization-algorithm= — =naive-bayes= or =maxent=; default =naive-bayes=. Change this through the Preferences page so Plauna can confirm and train the target model safely.
- =client-health-check-interval= — IMAP connection health-check period in seconds; default 60.
- =automatic-training-time= — local wall-clock time for the daily model training; default =02:00=.
- =time-zone= — IANA time zone used for training schedules, displayed dates and date filters; the system time zone is used initially.

Plauna keeps Naive Bayes and MaxEnt model files side by side. When you select a different model under "Admin" → "Preferences", Plauna opens a confirmation dialog. For the first switch, keep the option to use the current category assignments enabled and enter =Start training= exactly. Plauna then treats the current assignments as correct training examples. The previous model remains active until training of the complete target model succeeds; a failed switch therefore does not leave categorization without a usable model.

Both newly trained algorithms use namespaced features for sender address, sender domain, subject and up to 500 normalized body tokens. The displayed category confidence is the selected model's combined probability across those features, not three separate confidence values. A category or language changed manually is stored with 100% confidence because it represents an explicit user decision rather than a model prediction.

If you are upgrading from an earlier version that stored preferences in the database, Plauna migrates them into =settings.json= automatically on the first startup after the upgrade.

*** Order of Priority

When the same runtime value is provided more than once, Plauna uses the following priority:

1. CLI parameters
2. Environment variables
3. The file selected with =--config-file= or =CONFIG_FILE=
4. Built-in defaults


** Web UI Password Protection

The whole web UI is protected by one login name and password. The login name defaults to =root= for
new and existing installations and can be changed under "Admin" -> "Login Settings". When you open
Plauna you are redirected to a login page. After logging in, a signed session cookie keeps you signed
in until you log out (via the "Logout" link in the navigation bar) or the browser discards the cookie.
The signing key is persisted in =settings.json=, so a normal Plauna restart does not invalidate the
session.

*** How the password is determined

On startup Plauna decides which password is active using this order of priority:

1. The =PLAUNA_PASSWORD= environment variable, if set. This is authoritative on every start - if it is set, it overrides any password you changed in the UI the next time Plauna restarts.
2. A password you previously set in the UI (stored, hashed, in the database).
3. Otherwise, on first launch, Plauna generates a strong random password and prints it to the log. Look for a block like this in your logs:

#+begin_src
No web UI password configured. A temporary password was generated:

    Xk7p... (a long random string)

Log in as root and change it under Administration > Login Settings,
or set the PLAUNA_PASSWORD environment variable.
#+end_src

The password is never stored in plain text; only a salted PBKDF2 hash is kept in the database.

*** Changing the login name or password

Go to "Admin" -> "Login Settings". The login name and password have separate forms, and both changes
require the current password again. Login names are case-sensitive. A new password must contain at
least 8 characters and be entered twice. If =PLAUNA_PASSWORD= is set, the page warns you that a
password change will be reset to the environment variable's value on the next restart. The login
name remains the value selected in the UI.

*** Docker example

To set the password explicitly and persist the database, run, for example:

#+begin_src
docker run -d --name plauna -p 8080:8080 \
  -e PLAUNA_PASSWORD=your-strong-password \
  -v plauna-data:/var/lib/plauna \
  plauna:local
#+end_src

If you do not set =PLAUNA_PASSWORD=, check the container logs (=docker logs plauna=) after the first start to find the generated password.

*** Passwordless login with selected mTLS certificates behind NGINX

Plauna can turn a client certificate already verified by an NGINX reverse proxy into a normal
signed Plauna session. Only certificates whose SHA-256 fingerprint is explicitly configured bypass
the password. Requests without an allowed certificate continue to use the password login.

The allowlist and proxy secret can be managed under "Admin" -> "mTLS Login". Changes made there are
validated, written atomically to =settings.json= and activated immediately without a restart. The
proxy secret is write-only in the UI: an existing value is never sent back to the browser. Leave the
field blank to retain it, enter a value of at least 32 characters to rotate it, or use the explicit
delete checkbox. Clearing the fingerprint list disables new mTLS logins. Every change requires the
current admin password again, including changes made from an already authenticated browser session.

When an authenticated administrator opens "Admin" -> "mTLS Login" through NGINX with a verified
client certificate, Plauna shows its SHA-256 fingerprint there. If it is not trusted yet, the
administrator can add it to the UI-managed allowlist while saving the mTLS settings. The current
password is required again. The fingerprint is always derived from NGINX's protected certificate
header and is never accepted as a form parameter. With environment-managed configuration, the
settings page instead shows the fingerprint that must be added to
=PLAUNA_MTLS_TRUSTED_CERT_SHA256=.

The secret has to remain available to Plauna for request comparison and is therefore stored in plain
text in =settings.json=. Protect the data volume and do not share that file. It already contains the
similarly sensitive browser-session signing key.

Alternatively, configure mTLS through environment variables. A non-empty
=PLAUNA_MTLS_TRUSTED_CERT_SHA256= selects the environment as the complete, higher-priority source;
both values then appear read-only in the UI until the variables are removed and Plauna is restarted.

Set these environment variables on Plauna when using environment-managed configuration:

#+begin_src
PLAUNA_MTLS_TRUSTED_CERT_SHA256=AA:BB:...:FF,11:22:...:99
PLAUNA_MTLS_PROXY_SECRET=a-random-shared-secret-with-at-least-32-characters
#+end_src

The fingerprint list accepts commas, semicolons or whitespace as separators and accepts fingerprints
with or without colons. Get a fingerprint with:

#+begin_src sh
openssl x509 -in client.crt -noout -fingerprint -sha256 | cut -d= -f2
#+end_src

Generate the shared secret, for example, with =openssl rand -hex 32=. Configure the same value in
NGINX and forward only NGINX's own TLS variables:

#+begin_src nginx
server {
    listen 443 ssl;
    server_name plauna.example.com;

    ssl_certificate     /etc/nginx/tls/server.crt;
    ssl_certificate_key /etc/nginx/tls/server.key;

    ssl_client_certificate /etc/nginx/tls/client-ca.crt;
    ssl_verify_client optional;

    location / {
        proxy_set_header Host $host;
        proxy_set_header X-Plauna-Client-Verify $ssl_client_verify;
        proxy_set_header X-Plauna-Client-Cert $ssl_client_escaped_cert;
        proxy_set_header X-Plauna-Proxy-Secret "a-random-shared-secret-with-at-least-32-characters";
        proxy_pass http://plauna:8080;
    }
}
#+end_src

Use =ssl_verify_client optional= when users without a certificate should still see Plauna's password
login. With =ssl_verify_client on=, NGINX itself rejects clients that do not present a CA-trusted
certificate before Plauna can offer the password form.

The proxy secret is mandatory. It prevents a client that can reach Plauna directly from forging the
forwarded certificate headers. Still, do not publish port 8080: only NGINX should be able to reach
Plauna's HTTP listener. NGINX must overwrite all three =X-Plauna-*= headers as shown. If the allowlist
or secret is absent or malformed, Plauna fails closed and leaves mTLS login disabled.

*** Upgrading an existing Docker volume

Older Plauna images wrote files in the data volume as =root=. This fork now runs the application as the unprivileged =plauna= user. If a new container reports that it cannot delete or write a file below =/var/lib/plauna= (for example =train-eng.train=), repair the existing volume once while the container is running:

#+begin_src
docker exec --user root <container> chown -R plauna:plauna /var/lib/plauna
#+end_src

Retry the failed operation afterwards; a restart is normally unnecessary. This is only a migration step for an old volume, not a command that should be run on every start.

** Authentication

This section is about connecting Plauna to your *e-mail accounts* (not about logging in to Plauna itself - see "Web UI Password Protection" above).

Plauna supports basic (username/password) and OAuth 2 (XOAUTH2) authentication methods.

**** Basic Authentication

Basic authentication is very straightforward. Leave "Authentication" at "Basic" (it is the default value), enter your username and password. You will need to click at "Connect" on the "Connections" page in order to connect to the server. This is only needed during the initial set up. Plauna automatically tries to connect to every configured e-mail server on startup.

**** OAuth 2

Currently only tested for Gmail!

Prerequisites: You need your own application on Google Cloud, or Azure, or whatever e-mail provider you are using.

When you select "OAuth 2" on the connection screen, a new section called "Auth Providers" will appear underneath the connection details. You need to fill in a name (only for displaying on Plauna, you can choose whatever you like), the authorization and token URLs of your OAuth provider, the client ID and secret of your application, the scopes (separated by spaces), and a redirect URL. The redirect path is =/oauth2/callback=. If you're testing on localhost, use =http://localhost:{port}/oauth2/callback=. If you use a custom domain for Plauna, adjust the URL accordingly.

After saving the auth provider, select it in the connection configuration and click "Update Config". You can leave the "Secret" field empty; it is not used for OAuth 2.

After you set up your configuration, go to the "Connections" page and click on "Connect". On your first login, you will be redirected to your oauth provider in order to authorize the application you created to access your data. If everything is set up correctly, you will then be redirected automatically back to Plauna.

** Getting Started

When you start Plauna, it starts a web server on the port which you specified (defaults to 8080) and connects to the IMAP servers that you configured. You can use Plauna without configuring any IMAP servers but you would be missing out on the "move e-mail" functionality. On your very first start, the database is empty. You need to fill it with e-mails. There are three non-exclusive ways of doing this:

1. Go to "Admin". Under "Parse E-mails from Mbox", select an mbox file and click "Upload". You can see your e-mails under the "E-mails" tab shortly afterwards.

2. Go to "Admin" → "IMAP Connections", open an account, select a folder under "Parse E-mails from Folders", decide whether the messages should be moved after categorization, and click "Parse E-mails". You may also assign one category to the whole folder instead of using automatic category detection.

3. Just leave Plauna running and watch it save your e-mails. Beware: Depending on how many e-mails you receive on any given day, this method may be very slow.

   
** Language Detection

Plauna automatically detects the language of an e-mail when parsing it. Under "Admin" → "Languages", select the languages that should be used for training and categorization. Only languages that have already occurred in parsed e-mails appear there.

** Categorization

*** Create Categories

Go to "Admin" -> "Categories" to create and delete categories. When you create a category, Plauna tries to create its folder on every active IMAP connection. Deleting a category clears that category from affected Plauna metadata, but does not delete the corresponding folder or messages from the IMAP server. Plauna creates folders and moves messages as part of categorization; category administration itself does not remove server-side folders or messages.

*** Destination Folders

By default, e-mails of a category are moved to a sub-folder of "Categories" named after the category (e.g. =Categories/Work=). You can override this per category: in "Admin" -> "Categories" each category has a "Destination Folder" field, and the "New Category" form lets you set one when creating a category.

- Enter a full IMAP folder path using your mail server's hierarchy separator (e.g. =Archive/Newsletters= or =Archive.Newsletters=).
- Leave it blank to keep the default =Categories/<Name>= behaviour.
- Set it to the folder the mail is already in (e.g. =INBOX=) to *leave that category's mail in place* instead of moving it. More generally, whenever the source and destination folder are the same, Plauna performs no move.

Changing a destination folder does not move e-mails that were already filed; it only affects future moves.

*** Category Colors

Each category has a color, set with a color picker in "Admin" -> "Categories" (both on the "New Category" form and next to each existing category). The category dropdown on the e-mail list and on an e-mail's details page is color-coded with a left border matching the currently selected category, and on the e-mail list the category's color also tints the whole row at low opacity, so you can tell categories apart at a glance without it overpowering the row's text. A category created before this feature, or one for which an invalid color was submitted, falls back to a neutral gray.

*** Categorize E-mails

Under the tab "E-mails" you can edit the language and category of every e-mail directly in the list, or by clicking on an e-mail and changing it on the details page.

Changes in the list are saved *immediately* when you change a field - there is no "Batch Update" button to click:

- Changing an e-mail's *category* moves the e-mail to that category's folder on the IMAP server and saves the new category. If the move fails (for example when there is no active IMAP connection), the category is *not* saved so the stored metadata always reflects the e-mail's real location. Choosing "n/a" clears the category without moving the e-mail.
- Changing an e-mail's *language* saves it right away as well. Clearing the field removes the stored language.

Each field briefly outlines itself to show the result: green when fully saved, amber when the category could not be moved (and was therefore not saved), and red on unexpected failure.

If the IMAP message can no longer be found because it was deleted or moved outside Plauna, a nearby dialog asks "E-Mail konnte nicht gefunden werden. Trotzdem Kategorie ändern?". Choose "Ja" to update only Plauna's stored category or "Nein" to keep the previous value. Other IMAP failures are not overridden by this dialog.

On an e-mail's details page, the "Contents" section has a *Re-fetch from server* button. It re-reads that message from your IMAP server and fills in data that could not be extracted when the e-mail was first read - for example body text that was missed by an earlier parsing bug, and the detected language if it had never been set. Existing content and a language you set yourself are left untouched. The message is located by its Message-ID across your connected accounts, so the account must be connected for this to work.

The UI is responsive and works on phones, so you can recategorize e-mails on the go: the e-mail list keeps the category dropdown visible on small screens, and each change is saved instantly.

*** Filtering and Navigating the E-mail List

The filter bar above the list lets you narrow the e-mails down by:

- Metadata: all e-mails, enriched (categorized and language-detected) e-mails only, or e-mails without a category.
- Search Body: matches the e-mail's body content (not the subject - use the Subject column filter for that).
- A date range: click the date field to open a calendar and pick a start and end date (either may be left empty, and the "Clear" button next to it resets the range). The end date is inclusive.

The "Subject", "From", "To", and "Category" column headers each have an Excel-style filter: click a header to open a checklist of every distinct value that column has (for "From"/"To", every sender or recipient you've exchanged mail with; for "Category", every category plus "n/a" for uncategorized e-mails). Every value is checked by default, which means that column is unfiltered. Adjust the checkboxes and then choose:

- "Apply" to run the changed filter.
- "Reset" to select every value in that checklist again.
- "Cancel" to discard changes made since the popover was opened.

"Select all visible" ("Select all" in the category filter) only changes the checkboxes currently shown, which is useful after narrowing a long checklist with its search field. It does not apply the filter by itself. Checklist changes remain local until "Apply" is pressed.

Each checklist only offers values still reachable given your *other* active filters - for example, once you've picked a category, the "From" checklist only lists senders who actually have mail in that category, narrowing further as you add more filters. This matches how Excel's own column filters behave. The one exception is the category dropdown on each e-mail row (used to recategorize that e-mail): it always offers every category, regardless of the list's current filter.

All filters combine with AND: for example, you can search body text, pick two senders, restrict the list to a category and add a date range at the same time. Active filters are shown as removable chips above the table. Pagination controls appear both above and below the list, with "First", "Back", "Next" and "Last" buttons; the complete filter state is preserved as you page through the results. The number of e-mails shown per page can be set below the list from 1 to 500 (default 20).

On MariaDB, body search requires every entered word, supports prefix matching and accepts quoted phrases such as ="annual invoice"=. It uses the FULLTEXT index where possible; short terms, stopwords and punctuation-only searches transparently fall back to literal matching so they still return correct results. SQLite treats the complete input as a literal substring and is slower on large mailboxes.

*** Data Training

Under the "E-mails" tab, click "Train with Existing Data" to retrain the currently selected model with categorized e-mails. *Important:* You must have more than one category represented for each language you want to train.

You must have selected at least one language in "Admin" -> "Languages" in order to start training on your e-mails.

Plauna also trains the active model automatically once per day at the time configured under "Admin" → "Preferences". The configured IANA time zone controls that schedule. If Plauna was stopped at the scheduled time, it catches up the missed training after the next start; failures are logged and retried at the following scheduled run.

*** Choosing Naive Bayes or MaxEnt

The categorization model is selected under "Admin" → "Preferences":

- *Naive Bayes* remains the default and preserves compatibility with existing installations.
- *Maximum Entropy (MaxEnt)* considers the same combined sender, domain, subject and body features without Naive Bayes' feature-independence assumption.

The first time you switch to a model for which no complete model files exist, Plauna can train it from all current category assignments in the enabled training languages. The confirmation requires the exact text =Start training= to prevent accidental migration. Naive Bayes and MaxEnt files are stored side by side, so you can switch back to an already trained model without discarding either family.

*** Automatic Categorization

After training the selected model on the categories you created, Plauna categorizes each new e-mail and moves it automatically to the corresponding destination folder. The category confidence shown in the list is the probability produced during that automatic classification. Explicit category assignments, including a category forced during folder import, show 100% because they are user-provided rather than predictions.


* MariaDB

By default Plauna stores everything in a local SQLite file. For larger installations or heavy concurrent use (for example bulk categorization while browsing), MariaDB avoids SQLite's single-writer bottleneck and adds indexed FULLTEXT body search.

** Setting up MariaDB

Provide a MariaDB 10.6+ database and a user with full privileges on it, then tell Plauna how to reach it.

*** Via environment variables (recommended for Docker)

#+begin_src
PLAUNA_DB_TYPE=mariadb
PLAUNA_DB_HOST=db          # hostname or IP of the MariaDB server
PLAUNA_DB_PORT=3306        # default 3306
PLAUNA_DB_NAME=plauna
PLAUNA_DB_USER=plauna
PLAUNA_DB_PASSWORD=secret
#+end_src

Example docker-compose snippet:

#+begin_src yaml
services:
  plauna:
    build: .
    image: plauna:local
    ports: ["8080:8080"]
    environment:
      PLAUNA_PASSWORD: your-ui-password
      PLAUNA_DB_TYPE: mariadb
      PLAUNA_DB_HOST: db
      PLAUNA_DB_NAME: plauna
      PLAUNA_DB_USER: plauna
      PLAUNA_DB_PASSWORD: secret
    volumes:
      - plauna-data:/var/lib/plauna
    depends_on:
      db:
        condition: service_healthy

  db:
    image: mariadb:11
    environment:
      MARIADB_ROOT_PASSWORD: rootpw
      MARIADB_DATABASE: plauna
      MARIADB_USER: plauna
      MARIADB_PASSWORD: secret
    healthcheck:
      test: ["CMD", "healthcheck.sh", "--connect", "--innodb_initialized"]
      interval: 5s
      timeout: 5s
      retries: 20
    volumes:
      - mariadb-data:/var/lib/mysql

volumes:
  plauna-data:
  mariadb-data:
#+end_src

Place the Compose file in the repository root and start it with =docker compose up --build -d=. The =--build= flag ensures that the Plauna image is created locally from the current source tree.

The health check prevents Plauna from starting before MariaDB is ready. This matters because Plauna deliberately falls back to SQLite when the configured MariaDB server cannot be reached during startup.

*** Via the web UI

If you are already running Plauna on SQLite and want to switch:

1. Go to "Admin" → "Database".
2. Fill in the MariaDB connection details and click *Test Connection* to verify.
3. Click *Save Configuration* — this writes =db-config.edn= to the data directory.
4. Click *Start Migration* — Plauna will create the schema on MariaDB and copy all rows from SQLite. The SQLite file is not deleted.
5. Restart Plauna. It will now use MariaDB.

On the first start after upgrading to a version with FULLTEXT support, Flyway creates =idx_bodies_content_fulltext= on =bodies(content)= automatically. Creating the first FULLTEXT index can rebuild a large existing =bodies= table once, so that startup may take longer than usual. No separate search service or manually maintained index is required.

*** Notes

- Environment variables always override the saved =db-config.edn= file.
- If MariaDB is configured but unreachable at startup, Plauna logs an error and falls back to SQLite automatically. Check the startup log so an unavailable server does not go unnoticed; the fallback may contain an older or empty data set.
- Migrations are idempotent: running "Start Migration" again skips rows that are already present.
- The SQLite file remains untouched after migration; you can keep it as a backup.
- Plauna reads MariaDB's effective =innodb_ft_min_token_size=. Terms below that limit and words on the default InnoDB stopword list use a literal fallback, preserving correct search results.

* Debugging

** Logging

Plauna logs to standard output, so with Docker you can read the logs with =docker logs <container>= (add =-f= to follow). The log level can be changed under "Admin" -> "Preferences" (Error / Info / Debug). Increase it to "Debug" when you want more detail about what Plauna is doing.

** Diagnosing Freezes

If Plauna ever becomes unresponsive, the goal is to capture a *thread dump* - a snapshot of what every thread is doing - so the cause can be found. Plauna offers three ways to get one:

1. *Automatic deadlock watchdog.* A background task checks for thread deadlocks every 60 seconds. If it finds one, it logs the full stack traces of the involved threads at ERROR level (look for "Watchdog detected a deadlock"). This works even when the rest of the application is stuck, so the evidence ends up in your logs automatically.

2. *On-demand thread dump.* Open "Admin" -> "Thread Dump (debug)" (or visit =/admin/threads=). It returns a full thread dump in the browser and also writes it to the log. Use this when the UI is still responsive.

3. *Guaranteed dump via the JVM (recommended when fully frozen).* Send the JVM a quit signal; it prints a complete thread dump to standard output (your container logs) without affecting the running process:

#+begin_src
docker exec <container> sh -c 'kill -3 $(pgrep -f plauna-standalone.jar)'
docker logs <container> | tail -n 300
#+end_src

When reporting a freeze, please include the thread dump (and ideally the surrounding log lines) - that is what pinpoints which operation is blocked.

Uncaught exceptions in any thread are also logged, so a thread that dies unexpectedly still leaves an entry in the log.

** REPL

Plauna comes with a built-in REPL that can be activated on the administration page. It is hard-coded to listen to port 7888. If you know your way around Clojure and the codebase, you can use it to inspect the current state of the application or even make changes while it's running. Be aware that all your changes will be lost when you restart the application. If you are not debugging or do not know how to use the Clojure REPL, there is absolutely no reason to start it. There are no further features hidden behind it.
